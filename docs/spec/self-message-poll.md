# 本人真人消息定时补拉

## 目标

在现有群聊、私聊实时订阅之外，每轮完成后等待 5 秒，再从已启用会话的历史记录补拉当前登录用户发送的消息。消息按 `openMessageId` 去重后直接写入 `inbound_events`，继续交给该会话原有的 Codex session。

## 数据流

1. Host 建立实时订阅并完成启动离线补拉。
2. 读取当前 DWS profile 的 `userName`，作为历史消息的本人身份判据。
3. 逐个扫描已启用会话；群聊使用 `--group`，私聊使用 `--open-dingtalk-id`。
4. 从持久化扫描水位回退 2 秒，拉到“本轮开始时间减 5 秒”的固定截止时刻，让实时订阅先处理同一消息。
5. 仅保留发送者为当前用户的消息，不依赖 DWS 是否返回 AI 来源标记。
6. 复用 `Store.admitEvent`：已存在的 `message_id` 跳过，其余消息以 `self_poll` ingress 直接写入 inbox。
7. 会话查询串行执行；全部会话处理结束后等待 5 秒再执行下一轮。失败不终止实时订阅，也不推进失败会话的扫描水位。

## 持久状态

`self_message_poll_state` 只表达“历史源已成功扫描到哪里”，不替代 inbox 的业务水位。每个会话仅在该会话整段分页成功后更新 `scanned_through_at`。

## 实时与历史的分工

DWS 实时订阅可能收到“通过 AI 发送”的本人消息，也可能过滤钉钉客户端中本人真人发送的消息。Host 不猜测消息来源：实时通道有 5 秒优先窗口，历史补拉随后读取所有本人消息，两条路径最终由同一个 `message_id` 唯一约束合并。这样既不依赖不稳定的 AI 标记，也不会重复投递实时已经收到的本人消息。

## 性能边界

- 只扫描启用的 Conversation，并从各自持久水位增量读取。
- 同一轮固定截止时间，逐会话、逐页串行执行，不并发启动多个 DWS 命令。
- 使用递归定时器：上一轮完全结束后才等待下一轮间隔，不会因慢查询叠加轮次。
- 会话数量或消息量增加时，单个会话的实际补拉周期会自然变长，优先保护本机与 DWS 历史接口。

## 失败语义

- 单会话分页失败：保留原水位，下轮重试，依赖 inbox 唯一约束去重。
- 分页边界不推进：本轮失败，不推进水位。
- profile 无法解析当前用户：补拉器记录错误并继续实时订阅。
- Host 停止：中止等待，不再启动下一轮。
